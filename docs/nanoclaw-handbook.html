The NanoClaw Handbook

Everything needed to install NanoClaw from a terminal, wire it to your messaging apps, give it a personality and a memory, schedule its work, extend it with MCP tools and credentials, and run it day to day.

host: node + pnpm agents: docker + bun cli: ncl license: MIT
Part 01

What NanoClaw actually is

A single small Node process on your machine that orchestrates one Linux container per conversation, each running a Claude (or Codex, OpenCode, Ollama) agent.

NanoClaw is a personal AI assistant you host yourself. You talk to it from WhatsApp, Telegram, Discord, Slack, iMessage, Teams, Matrix, email, or your terminal. Behind each conversation is a Docker container running an agent that can read files, run shell commands, browse the web, call APIs, and write back to you.

The design bet is isolation over permission checks. The agent has full bash inside its container, which is safe because the container only sees what you explicitly mounted. There is no allowlist of "safe commands" to get wrong.

The one thing to understand: everything is a message

There is no IPC, no file watcher, no stdin piping between the host and a container. Each session owns exactly two SQLite files, and each file has exactly one writer.

The entity model

Four nouns explain nearly every configuration question.

EntityWhat it isExample
UserOne identity on one platform, id <channel>:<handle>telegram:6037840640
Messaging groupOne chat or channel on one platformYour Telegram DM; a Discord channel
Agent groupAn agent identity: its own workspace folder, memory, personality, container configgroups/andy/
WiringLinks a messaging group to an agent group and sets when it engages"this Slack channel → the Work agent, on @mention"
SessionRuntime unit: one (agent group, messaging group, thread) → one container + two DBsCreated automatically by the router

Privilege is attached to users, not agent groups. A user is an owner (global, full control), an admin (global or scoped to one agent group), a plain member of an agent group, or unknown.

Where things live on disk

PathContents
data/v2.dbCentral DB: users, roles, agent groups, messaging groups, wirings, container configs, approvals
data/v2-sessions/<group>/<session>/inbound.db + outbound.db for one session

Inside a container, the session folder is mounted at /workspace and the agent group folder at /workspace/agent.

Part 02

How this differs from just using Claude

Claude and Claude Code are things you open. NanoClaw is something that is already running.

NanoClaw uses the same underlying model and, by default, the same harness — it calls Claude through Anthropic's official Claude Agent SDK, so the agent has Claude Code's full toolset. The difference is not intelligence. It is persistence, reach, and autonomy.

CapabilityClaude appClaude CodeNanoClaw
Runs when you are not presentNoNoYes — background service
Reachable from WhatsApp / Telegram / SlackNoNoYes — 17+ channel adapters
Cron-scheduled work with run historyNoNoYes — ncl tasks
Memory that survives every session, foreverPartialProject files onlyYes — file-based memory/ tree
Spawns other persistent agents that message it backNoSub-agents die with the turnYes — create_agent
Shell accessNoYour machineIts container only
Credentials for third-party APIsConnectorsYour envInjected at an HTTPS proxy; never in the container
Modifies its own capabilitiesNoManuallyYes — approval-gated self-modification
Serves multiple people with separate memoryNoNoYes — per-agent-group isolation

What NanoClaw can do that Claude cannot do alone

  • Initiate. A scheduled task can wake at 06:00, gather data, decide nothing is worth reporting, and go back to sleep without costing a token — or decide it is worth reporting and text you.
  • Live in the channel you already use. No new app. Your assistant is a contact in WhatsApp or a bot in your team's Slack.
  • Accumulate a real institutional memory. Facts you tell it in March are in memory/ in November, as plain Markdown you can read and correct yourself.
  • Fan out. Your main agent can create a Researcher that works for an hour and reports back while you keep chatting.
  • Hold credentials it cannot read. The agent calls https://api.github.com/... and the proxy attaches auth. A prompt injection cannot exfiltrate a key the container never held.
  • Be edited. The codebase is small enough that "add this behavior" is a real answer, not a feature request.
The trade

You are now an operator. Something on your machine is running unattended with network access and shell access inside a sandbox. That is the whole value and the whole risk. Part 12 covers what to watch.

Part 03

What it is good for — and what it is not

Be honest with yourself here; it saves a weekend.

Good fit
  • A personal assistant you own. Briefings, reminders, research, drafting — reachable from your phone's messaging app.
  • Recurring, gated monitoring. "Watch this feed / API / repo and only bother me when something changes."
  • Long-horizon knowledge work. Anything where remembering last month's decision matters more than raw speed.
  • Small-team ops bots. One agent in a Slack channel with its own workspace and access list.
  • Privacy-sensitive work. Nothing leaves your machine except the model calls and the APIs you point it at.
  • Agentic coding on a schedule. "Review the week's commits every Friday and update the README if it drifted."
  • Learning how agent systems work. The codebase is genuinely readable end to end.
Bad fit
  • Multi-tenant SaaS. There are no accounts, no billing, no tenancy model. It is single-operator software.
  • Sub-second latency. A container spawn plus a model turn is seconds, not milliseconds. It is not a chatbot widget.
  • High-frequency polling. Ungated recurring tasks are capped at four fires a day by design. Frequent work needs a script gate.
  • A no-code product. Customization means editing code. That is the stated philosophy, not a gap.
  • Zero-maintenance appliance. Docker, a background service, and upstream updates are yours to manage.
  • Untrusted public exposure. Wiring an agent to a public channel with unknown_sender_policy: public means strangers drive an agent that holds your context.
  • Deterministic pipelines. If the answer must be identical every run, write a script and let the agent call it.
Part 04

Install it from the terminal

One script takes a bare machine to a named agent you can message.

Requirements

  • macOS or Linux (Windows via WSL2)
  • Node.js 20+ and pnpm 10+ — the installer installs both if missing
  • Docker Desktop (macOS/Windows) or Docker Engine (Linux)
  • Claude Code on the host, for /customize, /debug, the /add-<channel> skills, and automatic error recovery during setup

The whole install

# Clone and run. That is the install.
git clone https://github.com/nanocoai/nanoclaw.git nanoclaw-v2
cd nanoclaw-v2
bash nanoclaw.sh

nanoclaw.sh runs in two phases. Phase 1 bootstraps the toolchain (Node, pnpm, native module verification). Phase 2 is the interactive wizard: Docker check, Anthropic credential registration, agent image build, OneCLI vault install, mount allowlist, background service, timezone, and your first channel.

If a step fails, the script hands off to Claude Code to diagnose and resume from the break. Every step writes three levels of output: a clean summary in your terminal, a structured entry in logs/setup.log, and raw verbatim output in logs/setup-steps/NN-step.log.

The one interactive break

Anthropic credential registration hands the terminal to claude setup-token, which opens your browser for OAuth. This is the only step that breaks the wizard's visual flow, and deliberately so — NanoClaw does not re-implement or intercept the device flow. Your token goes into the OneCLI vault, never into the container.

Talk to it from the terminal first

Setup offers to create a terminal agent so you can verify everything works before pairing a phone.

# Send a message to your CLI-wired agent and print the reply
pnpm run chat hi

# If you skipped it during setup, create the CLI agent by hand
pnpm exec tsx scripts/init-cli-agent.ts --display-name "Max" --agent-name "Max's Terminal"

Running the service

# macOS (launchd)
launchctl load   ~/Library/LaunchAgents/com.nanoclaw.plist
launchctl unload ~/Library/LaunchAgents/com.nanoclaw.plist
launchctl kickstart -k gui/$(id -u)/com.nanoclaw   # restart

# Linux (systemd, user unit)
systemctl --user start nanoclaw
systemctl --user restart nanoclaw
systemctl --user stop nanoclaw

# Foreground, for development
pnpm run dev

Rebuilding the agent image

./container/build.sh

The buildkit caches the build context aggressively. --no-cache alone does not invalidate COPY steps — prune the builder first if you need a genuinely clean rebuild.

Uninstalling

bash nanoclaw.sh --uninstall             # interactive, confirms per group
bash nanoclaw.sh --uninstall --dry-run   # preview only, changes nothing
bash nanoclaw.sh --uninstall --yes       # skip prompts

Every install is tagged with a per-checkout id, so the uninstaller removes only that copy: its service, containers and image, data/, logs/, groups/, and that copy's OneCLI vault agents. The shared OneCLI app, your stored credentials, and any other NanoClaw checkout on the machine are left alone. Your .env is backed up first. Delete the checkout folder yourself to finish.

Migrating from v1

git clone https://github.com/nanocoai/nanoclaw.git nanoclaw-v2
cd nanoclaw-v2
bash migrate-v2.sh
Do not merge v2 into a v1 checkout

v2 is a ground-up rewrite. git pull into a v1 install produces conflicts that cannot be hand-resolved into a working system. Run migrate-v2.sh from a fresh clone, from a real shell — it needs interactive prompts and cannot run from inside a Claude Code session. It migrates state and leaves your v1 install untouched until you choose to switch the service over.

Channels and the isolation decision

Trunk ships no channel adapters. You install exactly the ones you want.

The codebase is the registry and infrastructure; the actual adapters live on a long-lived channels branch. Each /add-<channel> skill fetches that branch, copies the module in, wires its self-registration import, pins the dependency, and rebuilds. It is idempotent — safe to re-run.

Wiring a channel to an agent

The guided path is /manage-channels, which walks the isolation decision with you. The direct path:

# 1. Register the chat (usually created automatically on first message)
ncl messaging-groups create --channel-type telegram --platform-id 6037840640 \
  --name "Max DM" --is-group 0

# 2. Wire it to an agent group — by folder name, no id lookup needed
ncl wirings create --channel-type telegram --platform-id 6037840640 \
  --agent-group andy --session-mode shared --engage-mode mention

Omitted engagement flags default to whatever the channel adapter declares for that context (DM vs group chat). You override per wiring at creation; there is no per-instance config table.

Choosing an isolation level

The question that decides it: are you okay with any piece of information from one channel being available in the other?

Level 1
Shared session

Multiple channels feed one conversation. A GitHub PR comment and a Slack message sit side by side in the agent's context. Set session_mode: agent-shared.

Level 2
Same agent, separate sessions

One workspace, one memory, one personality — but independent conversation threads per chat. The common personal setup. Set session_mode: shared.

Level 3
Separate agent groups

Nothing shared. Different memory, different personality, different container. The right answer whenever different people are involved.

ScenarioLevel
Just you, across Telegram + Discord + SlackSame agent, separate sessions
Just you, three Telegram chats for three projectsSame agent, separate sessions
GitHub webhooks paired with the team Slack channelShared session
A chat with friend A and a chat with friend BSeparate agent groups
Personal channel and work channelSeparate agent groups
Team channel where members have different accessSeparate agent groups
Memory cross-pollinates

Levels 1 and 2 share the same memory/ tree. Something learned in one chat can surface in another. If there is a confidentiality boundary between two channels, that boundary must be a separate agent group.

Part 06

Personality, memory, and customization

Three different files, three different jobs. Editing the wrong one is the most common mistake.

What you want to changeWhere it goesApproval?
Role, tone, standing behavior rulesgroups/<folder>/instructions.prepend.mdnone
Durable facts, people, projects, decisionsgroups/<folder>/memory/none
Model, effort, assistant name, timezone, CLI scopencl groups config updateadmin
System / npm packages inside the containerinstall_packages or ncl groups config add-packageadmin
MCP tool serversadd_mcp_server or ncl groups config add-mcp-serveradmin
Host directories the agent can seencl groups config add-mountoperator only
NanoClaw's own source codeClaude Code on the host, or a builder sub-agentyou review the diff
Never edit groups/<folder>/CLAUDE.md

It is composed from scratch on every container spawn — from the shared base, your skill fragments, your MCP server fragments, and instructions.prepend.md. Your edits will be silently overwritten. Put standing instructions in instructions.prepend.md, which is imported first, at the top of the composed system prompt.

Setting a personality

Just tell the agent, in chat: "From now on, be terse. No preamble, no summaries. If I ask a yes/no question, lead with the answer." It writes that into its own instructions.prepend.md, and it holds from the next turn onward.

To do it by hand, or to seed a new agent:

cat > groups/andy/instructions.prepend.md <<'EOF'
You are Andy, Max's operations assistant.

## Voice
Direct and brief. No preamble. Lead with the answer, then the reasoning
only if it changes what Max should do.

## Standing rules
- Never send more than 5 lines to Telegram without being asked to expand.
- Money figures always carry the currency and the as-of date.
- When you are unsure, say so in one sentence and propose the check.
EOF

How memory works

Memory is plain Markdown on your disk. No database, no embedding store. It survives container restarts, session ends, context compaction, and switching the agent to a different model provider.

groups/<folder>/memory/
├── index.md              # Core Memory + a map of everything else — ALWAYS loaded
└── system/
    ├── index.md          # folder index
    └── definition.md     # how this agent's memory behaves — ALWAYS loaded

Whenever the provider opens a fresh context window — at startup, after a clear, after compaction — a session-start hook injects index.md and system/definition.md, each capped at 16k characters. Everything deeper is reached by following links from the index. That keeps the always-loaded footprint small no matter how big memory gets.

The tree is an Open Knowledge Format (OKF) v0.1 bundle: one concept per file, YAML frontmatter declaring a type (person, project, decision — the agent's own vocabulary, not a fixed list). Malformed frontmatter still works; the agent repairs it when it next touches the file. The payoff is portability across providers and tools.

Operator moves

Read or edit any memory file directly on the host — changes are picked up on the next context window. A wrong fact is just wrong text: delete it, or tell the agent it was wrong and let it prune. To carry memory across a provider switch, run /migrate-memory.

Container configuration

ncl groups config get --id <group-id>

ncl groups config update --id <group-id> \
  --model claude-opus-5 \
  --effort high \
  --assistant-name "Andy" \
  --timezone "Europe/Lisbon" \
  --max-messages-per-prompt 40 \
  --cli-scope group

Config changes are saved but do not take effect until the container restarts:

ncl groups restart --id <group-id>
ncl groups restart --id <group-id> --rebuild --message "ffmpeg is installed — verify it and tell Max."

--rebuild rebuilds the image first and is required after package changes. --message queues an instruction the fresh container acts on when it boots; without it, the container simply stops and comes back on the next user message.

What cli_scope controls

ValueWhat the agent can do with ncl
disabledNever learns ncl exists — the instructions are excluded from its prompt, and the host rejects any request.
group (default)Only groups, sessions, destinations, members, tasks, scoped to its own agent group. --id and group args are auto-filled; cross-group access is rejected; it cannot change its own cli_scope.
globalUnrestricted. Set automatically for the owner's agent by init-first-agent.

Timezones

Each agent group can override the install-wide timezone. It grounds that group's cron interpretation, --process-after parsing, and run-log stamps immediately; the container's TZ follows on the next respawn.

ncl groups config update --id <group-id> --timezone "Asia/Tokyo"
ncl groups config update --id <group-id> --timezone ""   # back to the install default

Agent templates

A template is a folder you stamp into a working agent: standing instructions, MCP servers, skills, and optional paused recurring tasks — but never secrets and never a provider.

ncl groups create --template sales/sdr --name "SDR Agent"

Templates resolve only from a local directory: templates/ by default, or NANOCLAW_TEMPLATES_DIR. There is no git URL, no remote fetch, and ../ escapes are rejected. To use a community template, copy it into templates/ yourself first. Stamping does not wire a channel — do that afterward.

The other route: change the code

NanoClaw deliberately has no configuration files for behavior. If you want different behavior, you edit the code, and the codebase is small enough that this is safe. From Claude Code in your checkout:

  • /customize — guided changes: new capabilities, trigger words, behavior
  • /learn — distill a repeatable workflow into a reusable skill
  • /update-nanoclaw — bring upstream changes into a customized fork without a merge nightmare
  • /update-skills — re-apply installed skills to pull their latest upstream code
Part 07

Sub-agents and multi-agent setups

Two different mechanisms with the same word attached. Picking the wrong one is the difference between a clean delegation and a container that never goes away.

SDK sub-agent — stateless
  • The agent's built-in Agent tool, inside its own container
  • Spins up, completes, returns, disappears
  • No workspace, no memory, no footprint
  • Blocks the turn until it finishes
  • Use for: one-off lookups, parallel searches, anything that ends before the user's next message
create_agent — persistent
  • A whole new agent group: its own container, workspace, memory, personality
  • Lives indefinitely until you delete it
  • Bidirectional addressable destination on both sides
  • Fire-and-forget — the call returns before the agent is up
  • Use for: companions that accumulate context, collaborators that work independently and report back

Creating a persistent agent

From inside a container, the agent calls the MCP tool:

mcp__nanoclaw__create_agent({
  name: "Researcher",
  instructions: "You are a research agent working for Andy. Andy sends you " +
                "open questions. Work independently, cite sources, and report " +
                "back with send_message({ to: 'parent' }) only when you have " +
                "a conclusion — not with progress updates."
})

What happens: a new agent group is created with its own folder under groups/; your instructions string becomes its instructions.prepend.md; and two destination rows are written, so the parent addresses the child by name and the child addresses the parent as parent. The child inherits the parent's effective provider, not the instance default — a child is never spawned on a runtime the parent cannot reach.

This is host-side privileged

create_agent writes to the central DB and scaffolds host filesystem state — something a confined container is otherwise architecturally barred from. Authorization is enforced on the host, not in the container: only a trusted global-scope group is allowed through directly. Everything else — including unknown config, which fails closed — is held for admin approval, and you get a card naming the requesting agent and the proposed child.

From the host, the same thing without the MCP layer:

ncl groups create --folder researcher --name "Researcher"
ncl destinations add --agent-group-id <parent-id> --local-name researcher \
  --target-type agent --target-id <child-id>
ncl destinations add --agent-group-id <child-id> --local-name parent \
  --target-type agent --target-id <parent-id>

Destinations are the ACL

An agent can only send to a target it has a destination row for. There is no ambient "send to anyone". The local_name is scoped to the sending agent, so two agents can call the same target different things.

ncl destinations list --agent-group-id <group-id>
ncl destinations add --agent-group-id <id> --local-name ops-slack \
  --target-type channel --target-id <messaging-group-id>
ncl destinations remove --agent-group-id <id> --local-name ops-slack

Wiring a channel creates the companion destination row automatically and projects it into any running container, so a new chat works without a restart. If an agent's reply is silently dropped as "unknown destination", a missing destination row is the first thing to check.

Gating agent-to-agent traffic

You can require a human to approve every message from one agent to another, without unwiring them. Policies are directed and per-pair — gate both directions with two rows. This is operator-only; agents cannot manage their own gates.

ncl policies set --from <child-id> --to <parent-id> --approver telegram:6037840640
ncl policies list
ncl policies remove --from <child-id> --to <parent-id>

A worked multi-agent shape

Front
Andy

Wired to your Telegram DM. Holds the relationship and the memory. Delegates rather than doing long work inline.

Worker
Builder

No channel wiring at all. Reachable only from Andy. Makes code changes under strict diff limits and reports back.

Worker
Researcher

Owns its own long-running inquiry and its own memory. Runs its own scheduled sweeps and pushes findings to parent.

The self-customize container skill ships a ready-made builder-agent prompt with the guardrails that make this work in practice: minimal scope, read before writing, hard diff-size limits (reject anything over 200 new or 150 modified lines in one task), no commits, no secrets, and an explicit report of what changed. The limits are the point — 150 lines is reviewable by a human; 500 is not.

Part 08

Scheduled tasks

The feature that turns an assistant into a colleague. Tasks run in their own system session, separate from any chat.

Creating a task

A task needs a --prompt plus either --recurrence (recurring) or --process-after (one-shot). Always pass --name so the id is readable.

Recurring — the first run comes off the cron gridncl tasks create --group <group-id> \
  --name "weekday briefing" \
  --recurrence "0 9 * * 1-5" \
  --prompt "Compile the weekday briefing and send it to telegram"
One-shot — --process-after requiredncl tasks create --group <group-id> \
  --name "call reminder" \
  --process-after "2026-09-14T18:00:00+03:00" \
  --prompt "Remind me to call Dana"

Inside a container, --group is auto-filled. Cron expressions and naive local timestamps are interpreted in the owning group's timezone (its override, else the install default). Task ids become <slug>-<hex>, e.g. weekday-briefing-a25c.

A task has no chat attached to it

If its output should reach a human, the prompt must say where to send it, using a destination name that agent actually has — telegram, ops-slack, parent. A task whose prompt just says "summarize the news" produces a summary that goes nowhere but the run log.

Reviewing tasks and their history

A task series behaves like a cron job: the live pending row is the next run, and the completed rows are its history. list renders that as a run-history table.

ncl tasks list                              # all groups (host default)
ncl tasks list --group <group-id>
ncl tasks list --status paused
ncl tasks get weekday-briefing-a25c         # full prompt, script, run counts, recent log

list gives you, per series: schedule, run count, failed runs, last fire, next fire, and a pointer to the run log. get adds the full prompt, the gate script, the origin session, and the last ~10 run-log lines.

Run logs are Markdown files under the agent's own workspace at groups/<folder>/tasks/<series-id>.md — readable directly on the host. Every run auto-logs its final text; the agent can add mid-run notes:

ncl tasks append-log --msg "one feed returned 403; continuing with the rest"

Inside a task run the series id is derived from the session, so the agent only supplies --msg. This writes a log line — it sends nothing to anyone.

Managing tasks

CommandEffect
ncl tasks run <id>Fire one extra run now. Does not consume a one-shot or advance a recurring series — the safe way to test. Works while paused.
ncl tasks pause <id>Stop firing; keep the series.
ncl tasks resume <id>Resume a paused series.
ncl tasks update <id>Change --prompt, --recurrence, --process-after, or --script. Pass "null" or "none" to clear recurrence or script.
ncl tasks cancel <id>Stop the live task, keep its history. --all is the kill switch for everything in scope.
ncl tasks delete <id>Hard-delete the series and its history. Irreversible.

Script gates — the feature that makes frequent tasks cheap

A task can run a Bash script before the agent wakes. The script decides whether waking the model is worth it. A gated fire that finds nothing costs zero tokens.

ContractRule
Interpreterbash
Timeout30 seconds
Output cap1 MB
DecisionThe last stdout line must be {"wakeAgent": <bool>, "data": {...}}
wakeAgent: falseRun is marked handled. Model never called. No tokens.
wakeAgent: trueAgent wakes with data attached to its prompt.
State between runsPersist under the group workspace, e.g. /workspace/agent/last-seen-id
 
A monitor that only wakes the agent when there is something to sayncl tasks create --group <group-id> \
  --name "alert watch" \
  --recurrence "*/15 * * * *" \
  --prompt "Investigate the alerts in the script data and notify me if serious" \
  --script 'c=$(curl -sf https://example.com/api/alerts | jq length) || exit 0
echo "{\"wakeAgent\": $([ "$c" -gt 0 ] && echo true || echo false), \"data\": {\"alerts\": $c}}"'

Rules that bite if ignored: print the JSON as the very last line, exit 0, keep data small (a summary, not a dump), never prompt for input, and always test with bash -c '<script>' before scheduling.

The frequency limit

Ungated recurring tasks are capped at 4 fires per day

Anything more frequent is refused. Two ways through: attach a --script gate (preferred — the gate makes quiet fires free), or pass --dangerously-override-recurrence-limit, which should only be used after a human has explicitly confirmed they understand the token and quota cost.

Failure backoff

A script that errors — timeout, nonzero exit, missing decision, invalid JSON — counts as a failed run and backs the series off: 2, 4, 8, 16, 32, then 60 minutes, holding at 60. After 8 consecutive failures the series auto-pauses with the reason in its run log. Fix the script, test it, then ncl tasks resume <id>.

A deliberate wakeAgent: false is a normal successful run and never triggers backoff. ncl tasks get <id> shows failed_runs alongside the log.

Talking to it instead

You never have to touch the CLI. "Every weekday at 9, send me the sales pipeline overview" creates the task. "Pause the Monday briefing" pauses it. "What tasks do you have running?" lists them. The CLI is what the agent uses underneath — and what you use when you want certainty.

Part 09

MCP servers, credentials, and host-side OAuth

The part with the most moving pieces. The organizing principle: the container never holds a secret.

Adding an MCP server

Three routes to the same container_configs.mcp_servers JSON.

1 — from the host, as operatorncl groups config add-mcp-server --id <group-id> \
  --name memory \
  --command pnpm \
  --args '["dlx","@modelcontextprotocol/server-memory"]' \

ncl groups config remove-mcp-server --id <group-id> --name memory

An MCP server may also ship an instructions field, which is composed into the agent's system prompt as a fragment at spawn time — that is how the agent learns what the tools are for, not just that they exist.

Restart, not rebuild

MCP servers need ncl groups restart. Packages need ncl groups restart --rebuild, because the image itself changes.

The credential model

Agents never hold raw API keys. Outbound HTTPS from the container is routed through OneCLI's Agent Vault, a proxy running on the host that injects credentials at the proxy boundary, matched by API host, at request time.

What the agent writes — no auth header anywherecurl -s "https://api.github.com/user/repos?per_page=10"
curl -s "https://gmail.googleapis.com/gmail/v1/users/me/messages?maxResults=5"

Standard clients (curl, fetch, requests, axios, Go's net/http, git) honor HTTPS_PROXY automatically, so this needs no code in the MCP server. The consequences are worth stating plainly: a prompt injection cannot exfiltrate a key the container never had, and revoking access is a vault operation, not a container rebuild.

Secret modes

Auto-created vault agents default to all mode — every stored secret whose host pattern matches is injected. If an agent is in selective mode it gets nothing until you assign, which shows up as a 401 from an API whose credential you know is in the vault.

onecli agents list                                          # check secretMode
onecli agents set-secret-mode --id <agent-id> --mode all
onecli agents set-secrets --id <agent-id> --secret-ids ...  # stay selective

No container restart is needed — the gateway looks secrets up per request.

OAuth2 that has to happen on the host machine

This is the question that trips people up: an OAuth flow needs a browser and a loopback redirect, and the container has neither. NanoClaw's answer is that OAuth never happens in the container. There are four host-side paths, in order of preference.

Path 1 · default
Connect it in the OneCLI dashboard

Open http://127.0.0.1:10254 in the browser on the host machine and connect the app there. The OAuth round-trip — consent screen, redirect, token exchange, refresh — happens entirely on the host. The container just calls the real API URL and the proxy attaches the token.

Path 2 · on demand
Let the agent hand you a connect link

Set nothing up first. The agent's first call returns 401/403 with a connect_url. It shows you that link in chat, you open it on the host and authorize, you tell the agent to retry. This is the common path and needs no advance configuration.

Path 3 · host-run server
Run the MCP server on the host, reach it from the container

When a server genuinely needs host resources — the system keychain, a local desktop app, a loopback OAuth listener — run it on the host and point the container at host.docker.internal. Linux gets --add-host=host.docker.internal:host-gateway automatically. The /add-ollama-tool and /add-atomic-chat-tool skills are working examples of this shape.

Path 4 · last resort
Mount the host credential directory

Some servers insist on reading a real token file. Mount that one directory read-only, and only that one. This is an operator-only action that a container can never perform for itself.

Path 4 — operator-only, allowlist-gated, restart required# 1. Allow the root, once, in ~/.config/nanoclaw/mount-allowlist.json
pnpm exec tsx setup/index.ts --step mounts --force -- --json \
  '{"allowedRoots":[{"path":"/Users/max/.config/some-tool","allowReadWrite":false}],"blockedPatterns":[]}'

# 2. Mount it into one group, read-only
ncl groups config add-mount --id <group-id> \
  --host /Users/max/.config/some-tool \
  --container /home/node/.config/some-tool --ro

ncl groups restart --id <group-id>
Read this before mounting anything under your home directory

The blocked-pattern list (.ssh, .aws, .gnupg, …) is checked once, against the realpath of the mount root, and does not descend. It stops you from naming one of those paths as a mount. It does nothing about what lives underneath an allowed root. Allowlisting ~ or ~/.config exposes every credential below it regardless of what the blocklist says. Mount the narrowest possible directory, read-only, and prefer any of Paths 1–3 over this one.

MCP servers that refuse to boot without an env var

Some servers check for a credential env var at startup even though the real credential should come from the proxy. Put a placeholder there — never a real key.

{
  "mcpServers": {
    "acme": {
      "command": "npx",
      "args": ["-y", "@acme/mcp-server"],
      "env": { "ACME_API_KEY": "onecli-managed" }
    }
  }
}

The same convention applies to credential files an MCP server needs on disk: write a stub with "onecli-managed" as every secret value, mode 0600. Files containing that marker are managed by OneCLI and must not be edited or deleted. The onecli-gateway container skill teaches the agent this flow, including that it must never ask you for a raw key or invent credential-setup instructions.

Human approval on credential use

The vault can hold a credentialed outbound request until a human approves it — enforcement the agent cannot argue its way around, matched on host + method + path. This is a two-sided flow, and both sides must be live:

  • Server side decides when to hold. As of onecli@2.2.5 this is configurable only through the web UI at http://127.0.0.1:10254 — the CLI's rules create --action accepts only block and rate_limit.
  • Host side routes the hold to a person. NanoClaw registers a long-polling callback and DMs an approver, resolved from the user_roles table in preference order: scoped admins for that agent group → global admins → owners.
Both halves or neither

If approvals are configured in the vault but the NanoClaw host callback is not running, every credentialed call hangs until the gateway times out. If the vault has no rule asking for approval, the callback never fires no matter how it is wired.

Anthropic credentials specifically

Setup registers your Anthropic credential (subscription OAuth token or API key) with the vault via claude setup-token on the host. If you would rather manage it in .env, the /use-native-credential-proxy skill opts out of the vault for that one credential. For a one-off experiment against any Claude-compatible endpoint:

ANTHROPIC_BASE_URL=https://your-api-endpoint.com
ANTHROPIC_AUTH_TOKEN=your-token-here

Privilege is per person, not per agent

There is no "admin agent". ncl roles and the command gate query user_roles directly on the host — there is no environment variable of admin ids and no container-side check to bypass.

What happens when a stranger messages your agent

Set per chat, with the default coming from the channel adapter's declaration for that context:

Drop reasons are specific and worth knowing: no_agent_wired (no wiring exists), no_agent_engaged (a wiring exists but the engage rules did not fire — usually a missing @mention), unknown_sender_strict, and unknown_sender_request_approval. When someone says "it ignored me", this table names the reason.

A new user's first minute

When a channel is first wired, the agent runs its welcome skill. It is deliberately not a feature dump: a short greeting, its name, a signal that it can do a lot, and a question — explore, or jump straight in? If they explore, it reveals capabilities one at a time (memory, spawning agents, scheduled work, research, building things, cards, files, self-extension), each in two to four sentences, with an offer to demo.

It always covers two more things before finishing: that sensitive actions require the user's explicit approval, and that the user controls who may talk to it. And it makes the interaction model explicit — there are no commands. People just talk.

Bootstrapping the very first agent

Run /init-first-agent from Claude Code. It resolves your identity on the channel, creates the agent, grants you owner, wires your DM, and triggers the welcome message through the normal delivery path — so a successful welcome also proves the whole pipeline works.

Approvals in practice

Privileged actions do not execute and then ask forgiveness. They return approval-pending immediately, a card goes to an approver, and only on approve does the action replay and run — with the approval row carried as the grant, re-running the same checks.

Approvers are chosen by preference: scoped admins for the agent group, then global admins, then owners — favoring someone reachable on the same platform the request came from.

ncl approvals list --status pending
ncl approvals get <approval-id>

Actions that hold: install_packages, add_mcp_server, create_agent from a non-global-scope agent, most ncl writes from inside a container, unknown-sender admission, and any credentialed call your vault rules gate. Notably not held: an agent managing its own group's scheduled tasks.

The ncl command reference

Every resource and verb. Filter the table, or run ncl <resource> help <verb> for live per-verb detail with flags and examples.

Shape and transport

ncl <resource> <verb> [<id>] [--flags]
ncl <resource> help              # fields, types, enums, verbs
ncl <resource> help <verb>       # one verb in depth
ncl help                          # everything available to you

On the host, ncl talks to the running service over a Unix socket at data/cli.sock. Inside a container, the same binary at /usr/local/bin/ncl uses the session DB as transport, subject to cli_scope. If the host CLI is not on your PATH, pnpm run ncl -- <args> is equivalent.

Conventions that apply everywhere

  • Flags are --hyphen-case; they map to underscore_case DB columns automatically.
  • list accepts any non-generated column as an equality filter. Default limit is 200 rows — override with --limit N. Rows come back newest first.
  • create is idempotent where a natural key exists — re-running a wiring or messaging-group create returns the existing row instead of erroring.
  • Write verbs called from inside a container return approval-pending immediately. That is not an error; the result arrives later as a system message.
  • open = no approval · approval = admin must approve · host only = never runnable from a container.

Operations and debugging

There is no dashboard. That is deliberate — the intended debugger is Claude Code with /debug. Here is what it, and you, will look at.

Where to look, in order

Querying the databases

Use the in-tree wrapper, not the sqlite3 CLI — the host setup deliberately avoids depending on that binary, and the wrapper goes through the better-sqlite3 dependency setup already installs and verifies. Output matches sqlite3 -list.

pnpm exec tsx scripts/q.ts data/v2.db "SELECT id, name, folder FROM agent_groups"

pnpm exec tsx scripts/q.ts \
  data/v2-sessions/<group>/<session>/inbound.db \
  "SELECT seq, kind, status, substr(content,1,80) FROM messages_in ORDER BY seq DESC LIMIT 20"

Two invariants worth remembering when reading raw rows: the host writes even seq numbers and the container writes odd ones; and every timestamp written from JS is ISO-8601 UTC with a Z. Anything shown to a human or an agent is rendered in the install (or group) timezone; --json, DB values, and operator logs stay ISO.

Resource limits and network lockdown

Containers are unbounded by default so existing workloads do not start getting OOM-killed on upgrade. Opt in through .env:

CONTAINER_CPU_LIMIT=2
CONTAINER_MEMORY_LIMIT=8g
CONTAINER_PIDS_LIMIT=512

# Egress lockdown: the credential gateway becomes the only route out
NANOCLAW_EGRESS_LOCKDOWN=true

Development loop

pnpm run dev          # host, foreground, via tsx
pnpm run build        # compile host TypeScript
pnpm test             # host tests (vitest)
pnpm run lint

./container/build.sh  # rebuild the agent image

# The agent-runner is a SEPARATE package tree on Bun — not a pnpm workspace
cd container/agent-runner && bun install
cd container/agent-runner && bun test
pnpm exec tsc -p container/agent-runner/tsconfig.json --noEmit
Two runtimes, two lockfiles

The host runs on Node with pnpm; the agent container runs on Bun. They share no modules — only the session databases. Never run pnpm install inside container/agent-runner/, and never run bun install -g for a CLI the agent invokes (that bypasses the supply-chain policy — pin it in the Dockerfile's pnpm global-install block instead). Container tests import from bun:test, not vitest.

Supply chain policy

The host tree sets minimumReleaseAge: 4320 (3 days) — a new package version must have existed on npm for three days before pnpm will resolve it. Two lists must never be edited without explicit human sign-off: minimumReleaseAgeExclude (and any entry must pin an exact version, never a range) and onlyBuiltDependencies (build scripts execute arbitrary code at install). CI, automation, and container builds use pnpm install --frozen-lockfile.

Ten things that will save you an hour

  1. Config changes need ncl groups restart. Package changes need --rebuild too.
  2. Never edit groups/<folder>/CLAUDE.md — it is regenerated every spawn. Use instructions.prepend.md.
  3. A scheduled task has no chat. Say where the output goes, in the prompt.
  4. approval-pending is a normal response, not an error.
  5. Container logs vanish on exit. Reproduce with pnpm run dev.
  6. "The agent ignored me" is usually engage_mode: mention in a group chat, or a missing membership. Check ncl dropped-messages list.
  7. "The reply vanished" is usually a missing destination row.
  8. Memory is shared across every session in an agent group. Confidentiality boundaries need separate agent groups.
  9. Frequent recurring tasks need a script gate, not an override flag.
  10. Mount the narrowest directory you can, read-only. The blocklist only checks the mount root and does not descend.
